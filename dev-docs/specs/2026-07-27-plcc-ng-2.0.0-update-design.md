# Update to plcc-ng 2.0.0 — Design

Issue: [#8](../issues/008-update-plcc-ng-2.0.0.md)

## Background

plcc-ng 2.0.0 ships fixes for the three upstream defects this repository
worked around while migrating V0–V2, tracked as issues
[#3](../issues/003-python-run-return-value-quoted.md) (Python `_run()`
return value printed with quotes),
[#4](../issues/004-js-var-field-reserved-word.md) (a `var` field breaks
the JavaScript target), and
[#6](../issues/006-multi-capture-alt-name-case-mismatch.md) (camelCase
alt-names flattened at runtime). Per the release's
[What's new](https://ourplcc.github.io/plcc-ng/latest/whats-new/):

- **`_run()` return behavior (breaking).** The entry point now returns
  its output as a string and the runtime prints it. Java's `_run()` goes
  `void` → `String`; Python and JavaScript must return a string. Direct
  stdout printing is no longer permitted. This **inverts** the #3
  workaround: the repo currently prints, and must switch to returning.
- **Alt-name casing fixed.** camelCase alt-names are preserved instead of
  flattened, and multi-word nonterminal captures decapitalize only the
  first letter. This resolves #6.
- **Reserved-word detection added.** A captured field name that collides
  with a target-language reserved word is now reported as a
  specification error at emit/run, instead of silently generating broken
  code. This makes #4's `var` field a hard error rather than broken JS —
  so an explicit, non-reserved name is still required.
- **LL(1) FOLLOW-set fix** for late-registered nullable productions.
- Documentation examples verified to be LL(1), compile, and run as
  written.

Only V0, V1, and V2 are migrated to plcc-ng today; the other 11 kept
languages are still old-format and migrate later. This work therefore
touches V0–V2 directly and establishes conventions the later migrations
inherit.

## Goal

Adopt 2.0.0, pin the toolchain reproducibly, and restore the original
course-material identifiers wherever 2.0.0 now permits — reducing the
divergence between the shipped languages and the materials that teach
them.

## Settled decisions

### The `SYMBOL` token (was `VAR`)

The original materials capture `<VAR>` into an auto-named field `var`.
`var` is a JavaScript reserved word, so it cannot be the field name in a
grammar shared across all three targets — and 2.0.0 now rejects it
outright rather than emitting broken JavaScript.

Rather than alias the field (`<VAR:...>`) in every grammar — a footgun
that must be remembered for all 14 languages, and silently reintroduces
the reserved-word error whenever it is forgotten — **rename the token
itself to `SYMBOL`**. The field then auto-names `symbol` with no alias,
and the default is always correct.

This is a correction, not merely a workaround: in V0–V6 a `SYMBOL` names
an *immutable* binding (a constant), not a mutable variable, so `VAR` is
a misnomer there; `symbol` is the generic term that stays accurate across
the whole V0→later arc, including the languages that do introduce
mutation. `symbol` is not a reserved word in Python, Java, or JavaScript
(only capitalized `Symbol` is a JavaScript global), so it clears 2.0.0's
detector.

- Token: `token VAR` → `token SYMBOL`.
- Capture: `<VAR:name>` → `<SYMBOL>` (field `symbol`).
- Semantics: `.name.lexeme` → `.symbol.lexeme`.
- **The AST node class stays `VarExp`** — it is a variable-*reference*
  expression, and "a `VarExp` holds a `symbol`" reads cleanly. Renaming
  it would balloon the blast radius (every `VarExp` reference plus the
  class dispatch) for no gain.

### `IfExp` children restored to camelCase

2.0.0 preserves alt-name casing, so V2's `IfExp` children return to the
original spelling:

```
current:   IF <Exp:testexp> THEN <Exp:trueexp> ELSE <Exp:falseexp>
restored:  IF <Exp:testExp> THEN <Exp:trueExp> ELSE <Exp:falseExp>
```

Semantics return to `.testExp` / `.trueExp` / `.falseExp`.

### Nonterminals stay PascalCase

plcc-ng requires PascalCase nonterminals; lowercase is not allowed, so
there is no decision to make here. `<Program>`, `<Exp>`, `<Prim>`,
`<Rands>` stay as they are.

### `_run()` returns a string

Required by 2.0.0. Per target:

- **Python:** `print(...)` → `return str(...)`.
- **Java:** `public void _run()` + `println` → `public String _run()`
  returning the string.
- **JavaScript:** already returns a string — verify unchanged.

### Reproducible toolchain pin

The devcontainer currently uses the floating tag
`ghcr.io/ourplcc/devcontainers/plcc-ng:1`, which is not captured in
`devcontainer-lock.json` and can drift silently. Pin to the specific
digest so "the version that fixed the bugs" is reproducible:

```
ghcr.io/ourplcc/devcontainers/plcc-ng:2.0.0@sha256:8e0123b52bd6bda9b60bb15d03d3b1922b9a56ce79565bd52bca195f6d3f0979
```

The `2.0.0` tag documents intent; the digest guarantees immutability. As
of this writing the `2.0.0`, `2`, and `latest` tags all resolve to this
same digest, confirming 2.0.0 is the newest release. Re-verify the digest
at implementation time in case a 2.0.x patch has since been published.

## Plan of work (phased)

The forced change (`_run()` returning) is separated from the optional
identifier restorations so the toolchain bump can be trusted green before
any cosmetic refactor lands on top of it. The current `<VAR:name>` and
lowercase `testexp` still work on 2.0.0, so they need not move in the same
step.

### Phase 1 — Adopt and de-break

1. Pin `.devcontainer/devcontainer.json` to the digest-pinned 2.x image;
   rebuild the container.
2. Fix `_run()` in V0–V2 across all three targets to return a string.
3. **Verify:** run the V0/V1/V2 bats suites (all three targets) to green.
   The load-bearing check: confirm a returned string now prints
   *unquoted* — that was #3's actual defect, and the whole approach rests
   on 2.0.0 having fixed it.

### Phase 2 — Restore identifiers

1. Grammars (V0/V1/V2): `token VAR` → `token SYMBOL`; `<VAR:name>` →
   `<SYMBOL>`.
2. V2 grammar: `<Exp:testexp>` → `<Exp:testExp>` (and `trueExp`,
   `falseExp`).
3. Specs: `.name` → `.symbol` (15 references); V2 `IfExp` semantics
   `.testexp` → `.testExp` etc. across all three targets.
4. Update — not append — the V0/V1/V2 entries in
   [course-material-impact.md](../course-material-impact.md): the field
   is now `symbol` via a *token* rename to `SYMBOL` (record the
   misnomer-correction rationale), and `IfExp`'s children are camelCase
   again. Flag `SYMBOL` as the standing convention for every language.
5. **Verify:** bats suites green again.

### Phase 3 — Close out

1. Close issues #3, #4, #6 via `bin/issues/close.bash`. Each is resolved
   by 2.0.0: #3 by returning a string, #4 by the `SYMBOL` rename plus
   2.0.0's detector, #6 by the alt-name casing fix.
2. Reconcile each issue's "pending approval to file upstream" note —
   2.0.0 shipped the fixes, so filing upstream is moot; record that in
   the closing commit.
3. Update the roadmap (handled by `close.bash`) and run
   `bin/issues/check.bash`.

## Out of scope

- The 11 unmigrated languages (V3–V6, NAME, NEED, OBJ, REF, SET, TYPE0,
  TYPE1). They inherit the `SYMBOL`, camelCase, and `_run()`-returns
  conventions when they migrate, not here.
- The `Val`/`Prim` per-language duplication (pre-existing; noted in the
  V2 lessons).
- Any nonterminal-casing change.

## Risks and watch-items

- **Returned-string quoting.** If 2.0.0 still quotes a returned string,
  Phase 1 is blocked; verify this first, before touching identifiers.
- **LL(1) FOLLOW-set fix.** The analysis change could in principle alter
  how an existing grammar is analyzed. Low risk given how simple the
  V0–V2 grammars are, but watch for it during the rebuild.
