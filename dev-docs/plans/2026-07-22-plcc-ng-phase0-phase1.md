# plcc-ng Migration — Phase 0 & Phase 1 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Remove the languages not used in course materials and stand up this repo's `plcc-ng` conventions (Phase 0), then port V0 — grammar plus Python, Java, and JavaScript semantics — as the syntax pathfinder for the rest of the migration (Phase 1).

**Architecture:** Phase 0 is pure deletion plus a small addition to the issue-tracking tooling (a `Target` field, so upstream `plcc-ng` defects found later can be tracked here and migrated out afterward). Phase 1 introduces the per-language directory convention every later phase will reuse: one shared `grammar.plcc` (lexical + syntactic sections) plus `python/`, `java/`, and `javascript/` subdirectories, each holding its own `spec.plcc` that `%include`s the shared grammar and adds one target's semantic section. Every command and code sample below was validated end-to-end against the `plcc-ng` CLI actually installed in this devcontainer before being written down here.

**Tech Stack:** `plcc-ng` CLI (`plcc-scan`, `plcc-parse`, `plcc-rep`, `plcc-python-emit`/`-run`, `plcc-java-emit`/`-build`/`-run`, `plcc-javascript-emit`/`-run`), `bats-core` (via `bin/test.bash`), bash, Python 3.12+, Java JDK 21+, Node.js 18+. All of these are already available in this devcontainer.

## Global Constraints

- Keep and migrate exactly these 14 languages: V0, V1, V2, V3, V4, V5, V6, SET, REF, NAME, NEED, TYPE0, TYPE1, OBJ. Everything else in `src/` is removed in Phase 0.
- Structural fidelity across targets: Python, Java, and JavaScript semantics for a given language must mirror the same class boundaries and method names the existing Java implementation uses — not be rewritten in a more "native" style per target. The only sanctioned exception is `_run()` itself: Python/Java call `print()`/`System.out.println()` directly; JavaScript must `return` the string (see Global Constraint below on `_run()`).
- `_run()` per target: Python and Java print directly from `_run()` and return `None`/`void`. JavaScript's `_run()` must `return` the string — writing to stdout directly from JS `_run()` corrupts `plcc-rep`'s output protocol.
- Every language-specific token capture whose auto-generated field name collides with a target-language reserved word must use an explicit `:fieldname`. Confirmed necessary for `VAR` (auto-name `var`, a JavaScript reserved word) — rename it in the one shared `grammar.plcc` (e.g. `<VAR:name>`), which fixes all three targets at once.
- Every test case gets one shared `<LANG>.input` / `<LANG>.expected` pair, asserted against by one `@test` block per target in a single `.bats` file — Python, Java, and JavaScript must produce byte-identical output for the same input.
- Any genuine `plcc-ng` bug or migration-guide inaccuracy discovered gets filed as an issue in **this** repo (`bin/issues/new.bash`), with `Target` set to `ourPLCC/plcc-ng` — never filed upstream directly without explicit confirmation first.
- Any change that affects something an instructor's course materials would need to match (a renamed field referenced in a semantics walkthrough, a changed output format, a renamed grammar symbol) gets logged in `dev-docs/course-material-impact.md`, under that language's heading, **in the same commit that makes the change** — not batched up for later. This is distinct from the defect-tracking rule above: that's for bugs in `plcc-ng` itself, this is for our own deliberate changes that ripple into how the language is taught.
- One issue and one roadmap entry per phase, closed via `bin/issues/close.bash` as that phase's final commit.
- This devcontainer has no old PLCC (`plcc`/`plccmk`) installed — only `plcc-ng`. All 31 pre-existing `.bats` tests currently fail here with `command not found` until their language is migrated. This is a pre-existing condition, not something either phase needs to fix beyond what V0's own migration naturally resolves.
- Full design context: [dev-docs/specs/2026-07-22-plcc-ng-migration-design.md](../specs/2026-07-22-plcc-ng-migration-design.md).

- [ ] **Step 1: Write `src/V0/grammar.plcc`**

```text
# Language V0
# primitive expressions
skip WHITESPACE '\s+'
skip COMMENT '%.*'
token LIT '\d+'
token LPAREN '\('
token RPAREN '\)'
token COMMA ','
token ADDOP '\+'
token SUBOP '\-'
token ADD1OP 'add1'
token SUB1OP 'sub1'
token VAR '[A-Za-z]\w*'
%
<Program>        ::= <Exp>
<Exp:LitExp>     ::= <LIT>
<Exp:VarExp>     ::= <VAR:name>
<Exp:PrimappExp> ::= <Prim> LPAREN <Rands> RPAREN
<Rands>          **= <Exp> +COMMA
<Prim:AddPrim>   ::= ADDOP
<Prim:SubPrim>   ::= SUBOP
<Prim:Add1Prim>  ::= ADD1OP
<Prim:Sub1Prim>  ::= SUB1OP
```

Notes on the translation, applying the migration guide plus this repo's own validated findings:
- `token`/`skip` keyword added to every lexical rule (guide undersold this).
- Nonterminals PascalCased: `<program>` → `<Program>`, `<exp>` → `<Exp>`, `<prim>` → `<Prim>`, `<rands>` → `<Rands>`.
- Alternative names moved inside the brackets after a colon: `<exp>:LitExp` → `<Exp:LitExp>`.
- `<VAR>` renamed to `<VAR:name>` — required so the JavaScript target doesn't collide with the reserved word `var` (see the Global Constraints above).
- No trailing `%include code` — the semantic section is added per-target in Tasks 7–9 instead of shared, since `plcc-ng` semantic sections are single-target.
- No third `%` separator here — this file ends after the syntactic section; each target's `spec.plcc` supplies its own semantic section after `%include`-ing this file.

### Task 7: Add V0 Python semantics

**Files:**
- Create: `src/V0/python/spec.plcc`

The current `src/V0/code` file (old PLCC, Java-only) — this is the reference structure every target mirrors:

```
# class methods

Program
%%%
    public void $run() {
        System.out.println(exp.toString());
    }
%%%

PrimappExp
%%%
    public String toString() {
        return prim + "(" + rands + ")";
    }
%%%

Rands
%%%
    public String toString() {
        String s = "";   // the string to return
        String sep = ""; // no separator for the first expression
        // get all of the expressions in the expression list
        for (Exp e : expList) {
            s += sep + e;
            sep = ",";   // commas separate the rest of the expressions
        }
        return s;
    }
%%%

LitExp
%%%
    public String toString() {
        return lit.toString();
    }
%%%

VarExp
%%%
    public String toString() {
        return var.toString();
    }
%%%

AddPrim
%%%
    public String toString() {
        return "+";
    }
%%%

SubPrim
%%%
    public String toString() {
        return "-";
    }
%%%

Add1Prim
%%%
    public String toString() {
        return "add1";
    }
%%%

Sub1Prim
%%%
    public String toString() {
        return "sub1";
    }
%%%
```

- [ ] **Step 1: Write `src/V0/python/spec.plcc`**

```text
%include ../grammar.plcc
%
Python

Program
%%%
def _run(self):
    print(self.exp)
%%%

PrimappExp
%%%
def __str__(self):
    return f"{self.prim}({self.rands})"
%%%

Rands
%%%
def __str__(self):
    return ",".join(str(e) for e in self.expList)
%%%

LitExp
%%%
def __str__(self):
    return self.lit.lexeme
%%%

VarExp
%%%
def __str__(self):
    return self.name.lexeme
%%%

AddPrim
%%%
def __str__(self):
    return "+"
%%%

SubPrim
%%%
def __str__(self):
    return "-"
%%%

Add1Prim
%%%
def __str__(self):
    return "add1"
%%%

Sub1Prim
%%%
def __str__(self):
    return "sub1"
%%%
```

Note: `_run` uses `print(self.exp)`, not `return str(self.exp)`. A validated `plcc-ng` quirk (see the design spec's addendum) wraps a plain string *returned* from Python's `_run()` in quotes; `print()` avoids it and matches Java's print-directly style besides.

Uses `self.lit.lexeme` / `self.name.lexeme` (the documented `Token.lexeme` attribute) rather than the old code's `lit.toString()` — `plcc-ng`'s Python `Token` doesn't have a documented `__str__`, so this is more robust than relying on undocumented behavior, and stays just as simple.

Edit the generated file (`dev-docs/issues/004-js-var-field-reserved-word.md`):

```markdown
**Target:** ourPLCC/plcc-ng

## Description

A grammar token captured with its auto-generated field name colliding
with a JavaScript reserved word produces JavaScript that fails to load.
Specifically, `<VAR>` (no explicit `:fieldname`) auto-names its field
`var`, and the JavaScript target's generated constructor uses that name
as a parameter (`constructor(var) { ... }`), which is a `SyntaxError` in
JavaScript (`var` is reserved).

## Steps to Reproduce

1. Grammar with `token VAR '[A-Za-z]\w*'` and `<Exp:VarExp> ::= <VAR>`
   (no explicit field name), targeting `javascript`.
2. `echo "x" | plcc-rep`
3. Actual: `SyntaxError: Unexpected token 'var'` while loading the
   generated `VarExp.js`. Expected: it runs, same as the Python/Java
   targets do with the same grammar.

Renaming the capture (e.g. `<VAR:name>`) works around it. Since `VAR` is
the conventional token name for identifiers across all of this repo's
languages, this repo now renames it everywhere a grammar is shared across
targets, rather than special-casing JavaScript.

## Notes

Found while validating [dev-docs/plans/2026-07-22-plcc-ng-phase0-phase1.md](../plans/2026-07-22-plcc-ng-phase0-phase1.md).
`plcc-ng` might reasonably want to either reject/rename reserved-word
field names at generation time, or document the restriction. Not filed
upstream yet — needs the repo owner's go-ahead first.
```
