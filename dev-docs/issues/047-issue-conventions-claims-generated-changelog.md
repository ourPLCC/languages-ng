# 047 - issue-conventions.md credits a CHANGELOG.md that does not exist

## Description

[issue-conventions.md](../issue-conventions.md) says the roadmap must not
duplicate shipped history, because that history already has three owners:

> The past already has three owners: `CHANGELOG.md` (generated by
> semantic-release), GitHub Release notes, and the closed issues
> themselves.

Two of those three are wrong:

- **`CHANGELOG.md` does not exist.** `git ls-files` matches no file by
  that name, and [.releaserc.yaml](../../.releaserc.yaml) configures no
  `@semantic-release/changelog` plugin, so nothing has ever generated one.
- **GitHub Release notes are empty** — see
  [#46](046-release-notes-generator-not-loaded.md). The Releases exist,
  but their bodies are blank.

So of the three owners the convention rests its argument on, exactly one
is real: the closed issue files.

The rule the passage defends is still right — the roadmap should stay
forward-looking, and closed issues do record the past. It is the
justification that is false, and it is false about the release pipeline
specifically, which makes it the kind of claim someone reasons from later.

## Notes

Fixing #46 makes the "GitHub Release notes" half true going forward,
though not retroactively for `v1.0.2` and earlier. That leaves a choice
for the `CHANGELOG.md` half:

1. **Correct the sentence** to name only what exists — the cheap fix, and
   enough on its own.
2. **Add `@semantic-release/changelog`** so the claim becomes true. This
   is a real decision, not a formality: that plugin writes a file into the
   repository, which requires `@semantic-release/git` to commit it, which
   means semantic-release starts pushing commits to `main` rather than
   only creating tags. [CONTRIBUTING.md](../../CONTRIBUTING.md) documents
   that the branch ruleset deliberately targets the `main` branch and not
   tags *because* semantic-release does not push commits today. Taking
   this option means revisiting branch protection and giving the workflow
   a token that can bypass it.

Option 1 unless someone actively wants a committed changelog. Recording
option 2's cost here so that if the question comes up again, the branch
protection consequence is already known rather than rediscovered.
